# 稳定数据采集系统差距分析

> **Status: HISTORICAL / SUPERSEDED AS CURRENT AUTHORITY（2026-08-25）**
> 本文保留 2026-08-13 的审计方法和原始判断，不再代表当前开放缺口。当前缺口以 [`gaps/current.md`](gaps/current.md) 为准，当前实现以 [`CURRENT_STATE.md`](CURRENT_STATE.md) 为准。

> 分析日期：2026-08-13  
> 目标：将当前项目完善为具备搜索采集、商品详情采集、任务调度、任务状态管理、数据存储、缓存、异常重试、日志、监控、测试、配置管理和 Web/API 管理能力的稳定数据采集系统。  
> 本文仅做现状对比和优先级判断，不包含代码实现。无法从当前代码、已有运行记录或测试确认的内容标记为 **UNKNOWN**。

## 1. 结论摘要

当前项目不是从零开始：**采集、调度、状态、存储、日志和 Web/API 的主要业务骨架已经存在**，并且形成了“FastAPI 调度服务 + Vue 管理端 + Android Agent + Oracle”的端到端形态；根目录还保留一套“PyQt6 + Playwright/BitBrowser + SQLite”的旧桌面采集链路。

距离“稳定系统”的主要差距不在页面或接口数量，而在工程与运行保证：

1. **可重复构建和启动尚未建立**：Python 缺依赖声明，当前 Node 环境无法构建 Web，Android 测试环境缺 JDK。
2. **任务可靠性不完整**：已有状态与部分重试，但缺少统一状态机、租约/超时回收、幂等、持久化重试队列和断网补偿的可验证保证。
3. **缓存基本不存在**：未发现通用缓存层、TTL、失效策略或分布式缓存。
4. **监控基本不存在**：只有健康检查、设备心跳、业务日志和简单汇总，缺少指标、告警、追踪和 SLO。
5. **测试明显不足**：Android 仅 3 个单元测试；服务端和 Web 没有项目自有自动化测试；关键端到端路径没有稳定回归。
6. **架构边界偏弱**：路由直接写 SQL，采集核心文件过大，前后端/Agent 契约手写，两套采集链路重复实现领域逻辑。
7. **配置与安全基线不足**：秘密存在源码默认值，配置分散，无环境校验、版本化配置和统一发布约束。

综合判断：当前系统处于 **“功能型原型/内部可运行系统”向“可运维、可恢复、可回归的稳定系统”过渡阶段**。在完成构建基线、任务可靠性、可观测性和测试闭环之前，不宜把现有功能数量等同于生产稳定性。

## 2. 判定标准

| 状态 | 含义 |
|---|---|
| 已存在 | 目标能力已有明确实现和主要调用链；不代表稳定性已经达标 |
| 部分实现 | 有局部代码或单机能力，但缺少关键机制、覆盖范围或验证 |
| 不存在 | 未发现对应的项目实现 |
| UNKNOWN | 代码不足以确认，且本次没有可复现运行证据 |

优先级定义：

- **P0**：阻断可重复运行，或直接威胁数据、凭据、任务一致性。
- **P1**：稳定系统必需，完成后才能形成可靠闭环。
- **P2**：提升扩展性、效率和维护性，适合在稳定基线后推进。
- **P3**：优化体验或中长期演进。

## 4. 分能力差距

### 4.1 搜索采集

**判断：已存在，但稳定性部分实现。**

已有：

- Android 通过无障碍服务驱动拼多多 App，`PddActions.kt` 与 `TaskEngine.kt` 实现搜索、列表遍历、排序和候选处理。
- 桌面链路通过 BitBrowser + Playwright 执行搜索，`list_parser.py`、`search_sort.py` 支持列表解析和排序采集。
- 服务端任务可携带关键词和目标行，Android Agent 可领取执行。

差距：

- 页面/控件变化是主要外部不确定性，但没有版本化选择器、页面签名或兼容矩阵。
- 没有可离线重复的列表页样本库和解析回归测试。
- 没有搜索成功率、空结果率、验证码/访问异常率、单关键词耗时等指标。
- Android 与桌面端重复实现搜索规则，修复可能不同步。
- 天猫、京东、抖音只有服务端常量/种子，完整采集器不存在。

稳定目标：拼多多搜索链路对固定样本和固定 App/Web 版本可重复，失败可分类、可重试、可观测；多平台在有独立适配器前不得标为已支持。

### 4.2 商品详情采集

**判断：已存在，但质量保证部分实现。**

已有：

- Android `DetailReader.kt` 和 `PddActions.kt` 提取名称、价格、销量、规格、SKU、批准文号、厂家、图片等。
- 桌面 `detail_parser.py` 实现详情和 SKU 价格解析。
- 服务端支持商品、图片、原始 JSON、变更记录、软删除和商品库映射。

差距：

- 解析文件体积大、页面操作与字段解析耦合，难以隔离测试。
- 缺字段级数据质量规则：必填率、范围、格式、跨字段一致性和异常样本隔离。
- 缺解析器版本、来源页面版本和采集证据关联，历史结果难追溯。
- 商品/图片重复上报的幂等性没有端到端证明。
- OCR 图片过滤存在，但 OCR 可用性、误判率和样本基线为 **UNKNOWN**。

稳定目标：将“页面获取”“解析”“标准化”“质量校验”“持久化”形成明确边界，并以脱敏样本回归字段准确性。

### 4.3 任务调度

**判断：已存在，但可靠调度部分实现。**

已有：

- 支持创建、审核、设备指定、优先级、Agent 拉取、进度、结束、异常、失败项重新下发。
- 设备有注册、在线/忙碌、心跳、连续运行和休息状态。
- Android `AgentCoordinator` 轮询服务端并启动本地 `TaskEngine`。

差距：

- 当前是数据库轮询领取，不是具备可见超时、确认、重投和死信语义的可靠队列。
- 未发现任务租约/lease、心跳续租、执行超时和服务端自动回收卡死任务的完整机制。
- 缺设备并发上限、按租户/平台公平性、背压和调度容量模型。
- 领取与设备状态更新虽在事务中，但并发 Agent 下的唯一领取需要压力/并发测试证明。
- 服务重启、Agent 崩溃、网络分区后的恢复语义为 **UNKNOWN**。

稳定目标：明确 at-least-once 或其他投递语义；以租约、幂等和补偿保证任务不会永久卡死或无控制重复执行。

### 4.4 任务状态管理

**判断：部分实现。**

已有：

- 服务端任务含 `pending/running/done/failed/cancelled`，任务项也有类似状态，另有审核状态。
- Android 使用 `running/finished/stopped/failed`，协调器再映射服务端状态。
- 桌面端又使用 `running/paused/stopped/finished/failed/interrupted`，Excel 行使用 `pending/running/hit/miss/error`。

差距：

- 同一概念存在三套枚举和转换，语义不一致。
- 状态迁移散落在路由、Agent 和桌面任务代码中，没有单一状态机定义。
- 没有任务版本号、乐观锁或事件序列，旧进度可能覆盖新状态。
- 暂停、取消、超时、重新排队、部分成功的业务语义没有统一模型。
- 未见周期性 reconciliation 修复设备 `CURRENT_TASK_ID` 与任务状态不一致。

稳定目标：建立服务端权威状态机、合法迁移表和并发更新保护；Agent 本地状态只作为执行状态并显式映射。

### 4.5 数据存储

**判断：已存在，但数据治理与一致性部分实现。**

已有：

- Oracle 保存平台、设备、任务、任务项、日志、商品、图片元数据、RBAC、账号、告警和异常。
- Android Room 保存本地任务和商品；桌面 SQLite 保存旧链路任务和商品。
- 图片/APK 落本地文件系统，支持 Excel/CSV 导出。

差距：

- Oracle 基线初始化与运行时补丁并存，没有正式迁移版本、checksum 和部署锁。
- 逻辑关系没有数据库外键；商品自然键缺少足够唯一约束。
- Room schema version 1 且没有 migration。
- 缺备份、恢复演练、归档、保留期限、容量阈值和磁盘清理策略。
- Oracle、Room、文件系统之间没有可审计的一致性修复任务。
- `T_GOODS_LIBRARY` 可能是表或兼容视图，两种部署语义分叉。

稳定目标：先定义数据权威源、自然键、幂等键和迁移规范，再补备份恢复与一致性巡检。

### 4.6 缓存

**判断：不存在。**

现有相关但不构成缓存体系的代码：

- `server.image_filter` 使用函数级 `lru_cache` 缓存 OCR 配置探测。
- `ws_hub`、`cast_state` 保存进程内连接状态。
- Web Pinia/localStorage 保存用户界面状态和 Token。

缺失：

- 无通用缓存抽象或 Redis/Memcached 等实现。
- 无缓存键规范、TTL、负缓存、主动失效、容量限制或命中率监控。
- 无多实例一致性方案。

优先级说明：缓存不是第一阶段前置条件。应先通过基线测试和指标确认数据库/计算热点，再为平台字典、权限、设备摘要或昂贵只读查询引入；不得用缓存掩盖错误 SQL 或状态一致性问题。

### 4.7 异常重试

**判断：部分实现。**

已有：

- 桌面配置有 `retry_times`，采集代码含局部重试和降级。
- Android 使用 `runCatching`、协调器轮询和局部重试。
- 服务端可把失败/取消的任务项重新生成任务。
- Oracle 事务异常会回滚。

差距：

- 没有统一错误分类：可重试、永久失败、访问限制、解析失败、数据校验失败混杂。
- 没有统一指数退避、随机抖动、最大重试次数和总时限。
- Agent 上报重试缺持久化 outbox；进程退出后是否丢失待上报数据为 **UNKNOWN**。
- 没有死信队列/失败工作台和自动恢复策略。
- 重试前置的幂等约束不足，可能重复商品、图片、计数或日志。

稳定目标：错误分类 → 重试策略 → 持久化待办 → 幂等消费 → 死信/人工处理形成闭环。

### 4.8 日志

**判断：部分实现。**

已有：

- 桌面端 Loguru + UI 回调。
- Uvicorn 访问/错误日志和外层文件重定向。
- Oracle `SJZQ_TASK_LOG`、`SJZQ_OP_LOG`、`SJZQ_TASK_ANOMALY`。
- Android 将部分执行消息和异常上报服务端。

差距：

- 日志格式与字段不统一，缺 `request_id/task_id/item_id/device_id/attempt_id` 全链路关联。
- 未见结构化 JSON、集中采集、检索、轮转、保留和磁盘阈值策略。
- 宽泛异常捕获会丢失堆栈或根因。
- 缺敏感字段分类与脱敏标准。
- 任务日志和运行指标混用，不利于告警和聚合。

稳定目标：日志服务于单次任务复盘，任何失败都能从任务追到设备、尝试、输入摘要、异常类别和最终处置。

### 4.9 监控

**判断：部分实现，接近缺失。**

已有：

- `/api/health` 返回服务、Oracle DSN 字符串、图片目录、前端构建和 OCR 探测信息。
- 设备 heartbeat 支持在线判定。
- dashboard/report 提供业务汇总；WebSocket 推送状态。

差距：

- 健康接口没有证明依赖可用性；返回配置细节不适合作为公开健康响应。
- 无标准 metrics endpoint、时间序列指标或分布式追踪。
- 无任务吞吐、排队时间、执行时长、成功率、重试率、字段完整率、设备离线率等核心指标。
- 无阈值告警、告警接收人、抑制/聚合、值班和处置手册。
- 无 SLI/SLO 和容量基线。

稳定目标：先覆盖“服务是否活着、依赖是否可用、任务是否推进、数据质量是否下降、设备是否异常”五类监控。

### 4.10 测试

**判断：部分实现，但不足以支撑稳定迭代。**

已有：

- Android：`AccessGuardTest`、`ProductTargetMatcherTest`、`DetailReaderTest`。
- 桌面：`run_test.py` 依赖真实 BitBrowser 和页面的手工端到端脚本。
- Python 全部源文件本次静态编译通过。

缺失或未验证：

- 服务端单元/集成测试不存在。
- Web 组件/API/端到端测试不存在。
- Android 测试本次因缺 JDK 未实际运行。
- 无 Oracle 测试 schema、数据库迁移测试、API 契约测试。
- 无任务并发领取、重复上报、Agent 掉线、服务重启等故障测试。
- 无采集页面/无障碍节点样本回归、性能测试和长期稳定性测试。

稳定目标：以任务端到端主链为测试金字塔中心，先建立可离线测试的领域逻辑和契约，再补少量真机/真实页面验收。

### 4.11 配置管理

**判断：部分实现。**

已有：

- 桌面 `config.json` + `ConfigManager`。
- 服务端 Pydantic Settings + `server/.env`/环境变量。
- Web Vite 配置和固定开发代理。
- Android Gradle 配置与 SharedPreferences 服务地址/设备键。

差距：

- 配置分散且命名、类型、默认值和优先级没有统一文档。
- 数据库/JWT/Android 签名秘密存在源码默认值或构建文件。
- 缺必填配置启动失败机制和环境合法性校验。
- 缺开发/测试/生产配置模板、配置版本、变更审计和回滚。
- 桌面配置含失效绝对路径；Web 未声明 Node engines；Android 构建依赖未形成可重复环境说明。

稳定目标：秘密与普通配置分离；启动时严格校验；配置来源、覆盖顺序、环境差异和变更责任明确。

### 4.12 Web/API 管理能力

**判断：已存在，但工程化与契约部分实现。**

已有：

- Vue 页面覆盖登录、设备、任务、商品、Excel、账号、报表、用户、角色、操作日志、设置、OTA 和投屏。
- FastAPI 提供对应 REST/WS，管理端有 JWT/RBAC。
- FastAPI 可托管 `web/dist`，Vite 开发环境有 API/media/WS 代理。

差距：

- 当前 Node v20.11.1 下 Web 构建失败，无法证明从当前源码生成可发布产物。
- Python requirements 缺 PyJWT，干净环境服务端无法按清单导入。
- HTTPException 与 `{ok:false}` 混用，API 错误模型不统一。
- Vue/Android 手写 API 字段，没有版本化客户端或契约测试。
- CORS 过宽；Agent/WS 设备认证、限流、请求大小和滥用防护不足。
- 同步 Oracle、Excel、OCR、文件/URL 操作可能占用请求线程，容量为 **UNKNOWN**。

稳定目标：先恢复可重复构建，再统一 API 契约、错误、鉴权、限流与慢任务边界。

## 5. 当前不存在的关键能力

以下能力未发现项目级实现，应明确列入后续范围，而不是视为已有功能的一部分：

1. 通用缓存层及 TTL/失效/命中率体系。
2. 标准应用指标采集与 metrics endpoint。
3. 告警规则、通知渠道和故障处置手册。
4. 分布式追踪或跨端统一 correlation/attempt 标识。
5. 持久化重试队列/outbox、死信队列和自动补偿流程。
6. 统一任务状态机与数据库并发版本控制。
7. 正式数据库迁移版本体系和自动迁移测试。
8. 服务端与 Web 自动化测试套件。
9. API 契约生成/契约测试。
10. CI 构建、测试、制品和发布流水线。
11. 备份恢复、归档、保留与容量管理机制。
12. 天猫、京东、抖音的实际采集适配器。

## 6. 架构问题

### 6.1 两套采集架构并存，权威链路不明确

旧桌面端和 Android Agent 都实现搜索、详情、匹配、状态与本地存储，但两者不共享领域模型、解析规则或测试样本。旧链路是否继续支持为 **UNKNOWN**。在此决策前继续同时扩展会扩大维护成本。

### 6.2 服务端分层不足

FastAPI router 直接包含 SQL、事务、状态迁移和响应转换。HTTP 层、业务层和数据层边界交叉，使任务可靠性逻辑难以单元测试，也会把 Oracle 方言扩散到业务入口。

### 6.3 任务状态不是单一权威模型

服务端、Android 和桌面端使用不同状态枚举；转换散落在各处。任务、任务项、设备和审核状态之间缺少显式不变量，是卡死、重复完成和计数漂移的主要架构风险。

### 6.4 同步请求承担重工作业

Excel 解析/生成、OCR、图片读取或下载以及同步 Oracle 查询位于 API 请求路径。缺少后台作业边界、超时、取消与容量隔离，可能导致慢请求拖累管理 API。

### 6.5 持久化边界碎片化

Oracle、Room、桌面 SQLite、图片文件、APK JSON 和进程内 WS 状态分别管理，缺少统一对象标识、幂等键和一致性巡检。服务重启或网络中断时的恢复责任不清晰。

### 6.6 核心模块职责过重

`PddActions.kt`、`TaskEngine.kt`、`detail_parser.py`、`server/routers/tasks.py`、`excel_match.py` 体积大且混合多个职责。稳定化前不应做无关重构，但应在测试保护下按明确边界逐步拆分。

### 6.7 契约重复手写

FastAPI、Vue 和 Android 分别声明/拼装字段和状态，缺少统一 OpenAPI 契约消费和兼容策略。接口升级容易在运行期才暴露问题。

### 6.8 可观测性不是架构一等能力

日志、业务表、心跳和 dashboard 是后加的局部能力，没有统一 telemetry 模型。无法稳定回答“任务为何卡住、哪类解析开始下降、哪台设备异常、最近发布是否回归”。

### 6.9 配置和发布边界不清晰

源码默认秘密、`.env`、JSON、SharedPreferences 和 Gradle 配置混合。仓库还包含构建产物与运行数据；没有 CI 或受支持工具链定义，导致当前源码是否能重建现有产物无法确认。

## 7. 优先级与实施顺序

### P0：先建立可运行、可验证、不会破坏数据的基线

1. **固定可重复工具链和依赖**：补齐 Python 依赖声明；确定 Node/JDK/Android SDK 版本；从干净环境构建服务端、Web、Android。
2. **移除源码秘密并建立启动校验**：数据库、JWT、签名秘密外置；缺失时明确失败；完成秘密轮换计划。
3. **定义服务端权威任务状态机**：统一任务/任务项/设备状态、合法迁移和终态；明确 Android/桌面映射。
4. **定义幂等与并发规则**：任务领取租约、进度序号、商品/图片上报幂等键、完成请求重复语义。
5. **建立数据库迁移基线**：把 init 与 runtime patch 统一为可版本化、可测试、单实例执行的迁移流程。
6. **建立最小自动化测试门禁**：服务端状态机/领取/上报集成测试，Android 现有单测可运行，Web 可构建。

P0 完成标准：新环境可按文档构建；同一任务在并发、重复请求、Agent 断线下不会静默丢失或不可控重复；核心迁移和测试可自动执行。

### P1：形成稳定运行闭环

1. **可靠重试**：错误分类、指数退避、持久化 outbox/待上报队列、死信和人工重放。
2. **结构化日志与关联 ID**：贯穿 request、task、item、device、attempt，定义脱敏和保留。
3. **监控与告警**：服务/依赖健康、任务推进、设备在线、采集成功率、解析质量、重试和延迟指标。
4. **采集回归样本**：搜索列表和详情解析建立固定样本、字段质量阈值和版本记录。
5. **数据一致性**：自然键/唯一约束、外键取舍、文件与数据库巡检、备份恢复演练。
6. **API 契约与错误统一**：明确版本、统一响应/错误，补 FastAPI↔Vue↔Android 契约测试。
7. **安全收口**：Agent 身份、WS 授权、TLS、CORS、上传/下载限制、限流。

P1 完成标准：关键故障能自动恢复或进入明确待处理状态；运营能通过指标和日志定位；解析回归与数据质量下降可被检测。

### P2：扩展性与性能

1. 在指标证明热点后引入缓存抽象和实现，定义 TTL、失效及降级。
2. 将 Excel/OCR/大文件等重任务移出同步 API 请求边界。
3. 在测试保护下拆分大型采集、任务和路由模块，形成 adapter/service/repository 边界。
4. 明确并执行旧桌面链路保留、冻结、共享规则或退役决策。
5. 建立容量测试、并发模型和多实例 WS/调度方案。
6. 完善 Room migration、数据归档和存储容量治理。

### P3：产品化与多平台

1. 统一管理端可观测性体验、失败工作台和运维工具。
2. 完善发布、OTA、灰度、回滚和版本兼容矩阵。
3. 在平台适配接口和测试基线稳定后，再逐个平台实现天猫、京东、抖音。
4. 更新完整 README、运行手册、故障手册和架构决策记录。

## 8. 推荐的阶段里程碑

| 阶段 | 目标 | 交付判定 |
|---|---|---|
| M0 基线恢复 | 项目可干净构建与启动 | Python/Web/Android 构建明确；依赖和环境文档完整；秘密不在源码默认值 |
| M1 可靠任务核心 | 任务可领取、执行、重试、恢复 | 状态机、租约、幂等、重复请求和断线测试通过 |
| M2 数据与质量 | 数据可追溯、可校验、可恢复 | schema 迁移、唯一性、质量规则、备份恢复和一致性巡检通过 |
| M3 可观测运行 | 故障可发现、可定位 | 指标、日志、告警、dashboard 和处置手册覆盖关键 SLI |
| M4 工程质量 | 修改可持续回归 | 服务端/Web/Android/解析样本测试进入统一门禁 |
| M5 扩展优化 | 性能和多实例可扩展 | 缓存/后台作业/容量测试按指标落地；再评估多平台 |

## 9. 关键 UNKNOWN 与决策前置

以下事项会改变实现方案，进入开发前需要通过运行环境或业务负责人确认：

1. Android Agent 是否是未来唯一主采集链路，旧桌面端是否仍需生产支持。
2. 当前 Oracle 的真实 schema、约束、数据规模、版本、备份和 `T_GOODS_LIBRARY` 类型。
3. 实际设备数量、任务吞吐、并发目标、允许延迟和成功率目标。
4. 服务端部署是否单实例，是否有反向代理/TLS，网络中断的典型时长。
5. 商品的业务唯一键、重复商品合并规则和图片保留规则。
6. 任务投递期望是 at-least-once、at-most-once 还是业务幂等后的近似 exactly-once。
7. 失败任务自动重试上限、人工审核边界和长期失败保留要求。
8. 日志、商品、图片、APK 的保留期限和合规要求。
9. 多平台是当前真实需求还是仅预留方向。
10. 已存在 `web/dist`、APK 与当前源码的对应版本及发布来源。

## 10. 最终判断

- **已经存在**：搜索采集、商品详情采集、基础任务调度、Oracle/Room/SQLite 数据存储、基础日志、Web/API 管理。
- **部分实现**：任务状态管理、异常重试、监控、测试、配置管理，以及上述已有能力的稳定性保障。
- **不存在**：通用缓存体系、标准指标/告警/追踪、持久化重试与死信、统一状态机、正式迁移体系、CI 门禁和完整多平台适配。
- **最高优先级**：不要先扩展新功能；先恢复可重复构建，统一任务状态与幂等，建立数据库迁移和最小自动化测试，再补可靠重试、日志监控和数据质量闭环。
